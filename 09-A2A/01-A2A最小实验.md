# A2A 概念、最小实验与 MCP 对比

## 1. 问题场景

数据 Agent 属于数据平台团队，报告 Agent 属于办公平台团队，二者使用不同语言和框架。调用方不应了解对方内部 prompt、工具和状态机，只需发现能力并委托任务。这是 A2A 比“同进程创建两个 Agent 对象”更典型的场景。

## 2. 先理解的对象

- Agent Card/能力发现：对方是谁、能做什么、如何连接。
- Message/Part：文本、文件或结构化数据怎样表达。
- Task：一次可持续、可更新状态的工作，而不只是 HTTP 请求响应。
- Artifact：任务产生的报告或结果。
- Streaming/异步：长任务如何报告进度和完成。

字段名称与版本以 [最新规范](https://github.com/a2aproject/A2A/blob/main/docs/specification.md) 为准。

## 3. 两阶段实验

### 阶段 A：自定义 HTTP

自己定义 `/agents`、`/tasks`、`/tasks/{id}`。记录你必须私下约定的发现、状态、错误、取消、文件和认证字段。

### 阶段 B：A2A

使用当前 SDK/示例实现同一任务。比较减少了哪些私有约定、增加了哪些协议和部署成本。

## 4. 与 MCP 对比表

| 问题 | MCP | A2A |
|---|---|---|
| 对方通常是什么 | 工具/资源服务 | 独立 Agent 系统 |
| 调用方是否掌控流程 | 通常更强 | 对方内部可不透明 |
| 核心交互 | 发现并调用能力 | 委托、协作和任务状态 |
| 本项目优先级 | P0 | P2 |

同一个系统可同时使用：数据 Agent 通过 MCP 查数据库，再通过 A2A 把结果交给独立报告 Agent。

## 5. 安全问题

跨 Agent 身份、授权委托、数据最小化、任务取消、artifact 下载权限、跨服务 trace 和审计。不要因为对方叫 Agent 就默认可信。

## 6. 验收

能画出一个含 Host、MCP Server、两个 A2A Agent 的架构图，并逐条说明认证主体、数据流、失败和取消如何传播。
