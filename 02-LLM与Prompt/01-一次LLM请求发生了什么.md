# 一次 LLM 请求发生了什么

## 1. 从文字到 token

模型不直接理解“汉字”或“单词”，输入先被 tokenizer 切成 token，再映射为数字 ID。token 数不等于字符数；中文、英文、代码和 JSON 的比例不同。上下文窗口计算的是输入与输出 token 总量，并且会影响成本和延迟。

你应记录：模型名/版本、输入 token、输出 token、总耗时、首 token 延迟、状态和错误，而不是只保存答案。

## 2. 消息不是普通字符串

常见消息角色：

- system：系统边界、安全与全局行为。
- user：用户目标和输入。
- assistant：模型历史输出。
- tool：外部工具执行结果。

模型最终看到的是一段被 provider 按模板序列化的上下文。不同角色有不同优先级，但不能把安全完全寄托在“模型会听 system”。真正权限仍由代码和数据层执行。

## 3. 生成是概率过程

模型每次预测下一个 token 的概率分布，然后按解码策略选择。`temperature` 越高通常越随机；事实问答、抽取和工具参数可从较低温度开始。不要把 temperature 当作“事实正确率旋钮”。

设置 `max_tokens` 是输出预算，不保证答案恰好达到该长度。流式输出只是更早展示 token，不减少总计算量。

## 4. 为什么会幻觉

模型的默认目标是生成符合上下文的后续文本，不是查询事实数据库。出现错误可能因为：

1. 训练知识缺失或过期。
2. 问题含糊或上下文冲突。
3. 检索/工具返回了错误证据。
4. 模型没有忠于证据。
5. 输出格式正确但内容语义错误。

对应方法分别可能是澄清、RAG、工具调用、引用/验证、结构化输出与评测。不是所有错误都靠“再写一个 prompt”解决。

## 5. 结构化输出

业务程序通常需要 JSON 而非自然语言。优先使用 provider 或框架支持的 schema/structured output，并用 Pydantic 二次校验：

```python
from pydantic import BaseModel, Field

class Intent(BaseModel):
    category: str
    confidence: float = Field(ge=0, le=1)
    needs_tool: bool
```

校验失败后的策略要有限：重试一次、降级到人工/规则、或返回清晰错误。无限让模型修 JSON 会产生失控循环。

## 6. 最小请求的工程边界

```text
API 入参校验 → 构造消息 → 设置 timeout
→ 调模型 → 解析/校验输出 → 记录 usage/trace
→ 返回业务响应
```

还应考虑：密钥从环境变量读取、429/5xx 重试、并发上限、用户取消、敏感内容脱敏、模型版本变化和成本上限。

## 7. 验收问题

- token、字符、单词有什么区别？
- context window 为什么包含历史、检索和工具结果？
- 低 temperature 为什么不能消灭幻觉？
- JSON 能解析为什么不等于业务正确？
- streaming 改善的主要是总延迟还是感知延迟？
