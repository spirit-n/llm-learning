# 从零搭建 RAG

## 阶段 0：准备可公开数据

不要把前公司内部文档上传或提交 Git。可选公开技术文档、自己写的指标口径、开源项目文档。先选 20～50 篇，保留原始文件与来源。

## 阶段 1：解析与清洗

输出统一 `Document`：

```python
{
  "doc_id": "stable-id",
  "text": "正文",
  "source": "url-or-path",
  "title": "章节",
  "version": "2026-01",
  "tenant": "demo",
  "page": 3
}
```

抽样查看解析结果。常见问题：PDF 双栏顺序错、页眉重复、表格散列、编码乱码、导航栏混入正文。解析质量差时，后面换 embedding 没用。

## 阶段 2：Chunk

先做两个基线：

- 固定/递归：如 400～800 token，少量 overlap。
- 标题感知：保留章节路径，按自然边界切。

再按失败选择 parent-child 或语义切分。每个 chunk 保存 `chunk_id`、父文档、顺序、标题、权限和版本。

## 阶段 3：Embedding 与索引

embedding 把 query/chunk 映射为向量。模型选择要考虑语言、领域、维度、最大长度、许可证、延迟和是否归一化。写入向量库时同时写 metadata，以便权限和版本过滤。

验证三件事：相同文本距离近、专有名词能否召回、超长文本是否被截断。

## 阶段 4：检索

先实现 dense top-k，保存每次 query、候选 ID、分数和耗时。然后增加 BM25/sparse，使用 RRF 融合排名。RRF 基于名次而非直接混合不同量纲的分数。

## 阶段 5：Rerank

从 hybrid 取较大候选集，例如 20～50 个，再让 cross-encoder/late-interaction 模型精排，最后取 5～10 个。记录额外延迟。若正确证据根本没召回，reranker 无法凭空找回。

## 阶段 6：Context Builder

- 权限过滤应在检索层/数据层完成。
- 去重相邻重叠 chunk。
- 按来源和版本解决冲突。
- 计算 token 预算，保留问题最相关的证据。
- 为每段加不可伪造的内部引用 ID。

## 阶段 7：生成

明确要求仅根据证据回答、证据不足拒答、每个事实带引用。生成后验证引用 ID 是否存在、引用文本是否真的支持陈述。不要只检查“答案里出现了 [1]”。

## 阶段 8：更新与删除

设计稳定 doc/chunk ID。文档更新时标记新版本并删除/失效旧 chunk；删除数据时要同时处理向量、关键词索引、缓存和派生评测数据。

## P1/P2 扩展选择

- Query rewrite/Multi-query：用户表达与文档语言差异大。
- HyDE：用假想答案辅助召回，但需评估偏移。
- Parent-child：小块匹配，大块返回上下文。
- Multimodal RAG：解析图片/表格并建立跨模态证据。
- GraphRAG：需要全局实体关系或多跳时再评估，不是普通问答默认方案。

## 固定 RAG 与 Agentic RAG 的分界

[微软 Agentic RAG 章节](https://github.com/microsoft/ai-agents-for-beginners/tree/main/05-agentic-rag) 描述了迭代式 maker-checker：Agent 检索后评估结果，必要时改写问题、调用其他工具或再次检索，直到满足完成条件或交给人工。

这不是“普通 RAG 加一个 Agent 名字”，而是多了一套循环决策：

```text
制定检索动作 → 检索/调用工具 → 检查证据
→ 足够：生成并验证
→ 不足：改写/换来源/澄清（有限次数）
```

适合：复杂多源查询、数据库诊断、必须逐步验证证据的任务。普通单文档问答、FAQ 和低延迟场景通常先用固定 RAG。

### 对照作业

在相同 30 条样本上比较：

- 固定 hybrid RAG：每题固定检索一次。
- Agentic RAG：最多 3 次检索，可改写 query 或选择数据源。

同时报告任务正确率、平均检索次数、P95 延迟、token/成本、重复循环率和人工介入率。若质量只提高很少而成本翻倍，就不采用 Agentic 版本。
